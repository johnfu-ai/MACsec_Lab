## 8.3 多成员 CA 与组密钥

CA 是**组密钥联盟，不是点对点配对**：任何配置了相同 CAK/CKN 的端口都加入同一个 CA。把 8.1 的拓扑加上第三个成员，就得到了本节的三成员 CA——这也是理解 MACsec 组密钥能力边界的最佳模型：一把钥匙大家用，方向各自管。

### 8.3.1 三成员拓扑

```
        node-a (Key Server, prio 16)          10.10.0.10
       /            \
   node-b (32)     node-c (48)               10.10.0.20 / .30

  A distributes SAK#1 once (group-keyed)
  A→B, B→C, C→A each transmit on their own SC (own SCI, own PN space)
  every data frame carries explicit SCI (SC=1) — the ES=1 no-SCI
  shortcut is only valid for a two-member CA
```

图 8-3：三成员 CA 拓扑

### 8.3.2 一把 SAK、三条 SC

三个成员、一个 Key Server、**一把** SAK 发给全体（组密钥的分发成本不随成员数增长）；但三个发送方向各自维护独立的 SC——自己的 SCI、自己的 PN 空间。接收端为每个远端成员实例化一个 RX SA，键是 (SCI, AN)。

由此得到一个初看反直觉的结论：**三帧 PN=1 可以共存而不构成重放**——它们属于三条不同的 SC，PN 空间互不相干。判断重放永远要先问"哪个 SC"，再问"PN 多少"（重放窗口的完整裁决见 [6.3 抗重放窗口](../06_lifecycle/6.3_replay_window.md)）。

### 8.3.3 SCI 为什么必须显式携带

两成员 CA 里，接收端只有一个潜在对端，可以 ES=1 省略 SCI；多成员 CA 里接收端无法从源 MAC 唯一推断 SCI 的 PortID 部分，每帧必须 SC=1 显式携带 SCI。这是"协议字段的存在理由取决于拓扑"的典型例子。

逐帧解析见 [`captures/decoded/18-mka-multi-peer.md`](../captures/decoded/18-mka-multi-peer.md)（对应 [`captures/mka-multi-peer.pcap`](../captures/mka-multi-peer.pcap)）。而"一把钥匙大家用"的代价——成员之间互相不可区分、任何成员都能解密全组流量——将在 [9.5 PSK 弱口令与组密钥的固有问题](../09_attacks/9.5_psk_group_keys.md)正面讨论。把这套拓扑搬到真实线上重放的方法（netns + veth + 网桥），见 [10.4 Live 实验](../10_lab/10.4_live.md)。
