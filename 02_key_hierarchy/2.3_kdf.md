## 2.3 KDF 公式与标签

"标签差一个字节，整套密钥全错"——这是实现 MACsec 时最隐蔽的一类 bug。这一节给出 KDF 的精确公式，并特别标注两处容易踩坑的字节长度细节。

### 2.3.1 PRF：AES-CMAC

KDF 的 PRF = AES-CMAC，采用 NIST SP 800-108 计数器模式（IEEE 802.1X 6.2.1 / 6.2.2）。所有派生密钥都由同一套结构产出：`KDF(key, label, context, length)`，区别只在 key、label 与 context。

### 2.3.2 KEK / ICK：12 字节标签

KEK / ICK 的 label **恰好 12** 个 ASCII 字节（含空格）：

```
KEK = KDF(CAK, "IEEE8021 KEK", CKN[0:16], 128)
ICK = KDF(CAK, "IEEE8021 ICK", CKN[0:16], 128)
```

注意两点：label 里的空格是标签的一部分，少一个空格就派生出完全不同的钥匙；context 取的是 CKN 的前 16 字节，这也是 CKN 虽"不是密钥"却参与密钥派生的原因。

### 2.3.3 EAP 派生 CAK / CKN：16 字节标签

EAP 路径（本实验室未跑完整 EAP-TLS，只从 MSK 起算）：

```
CAK = KDF(MSK[0:cak_len], "IEEE8021 EAP CAK", mac1||mac2, CAKlength)
CKN = KDF(MSK[0:cak_len], "IEEE8021 EAP CKN", Session-ID||mac1||mac2, 128)
```

这里的 label 是 **16** 字节（`IEEE8021 EAP CAK` / `IEEE8021 EAP CKN`），与 KEK/ICK 的 12 字节标签不同——同一个 KDF，两套标签长度，是实现时的高频错误点。

`mac1` 是数值较小的 MAC，`mac2` 是较大的（802.1X 6.2.2）。两端按同一规则排序，保证各自算出的 context 一致。

### 2.3.4 谁不需要交换什么

持有相同 CAK+CKN 的成员**不必交换 KEK/ICK**——各自独立计算，结果必然一致，这是 KDF 的意义所在。SAK 正相反：只有 Key Server 生成，必须经 MKA 分发（AES-KeyWrap 封装）才能到达对端。

一句话总结：**能算出来的不用传，传过来的必然是算不出来的**（SAK）。想验证这些公式，可以直接改 [`tests/test_protocol.py`](../tests/test_protocol.py) 里的 KDF 断言，看哪条先挂。
